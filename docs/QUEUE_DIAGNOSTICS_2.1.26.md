# Очереди и замеры 2.1.26

02.11.2026. Пользователь выбрал защиту TPS при перегрузке. Уже принятые
worker-задания сохраняют порядок и ожидают downstream при необходимости.
Новый серверный захват использует offer без ожидания свободного места.
Если приём невозможен, включается явная аварийная остановка захвата.
Подробности и восстановление: [2.1.26](RELEASE_2.1.26.md).

## Отчёт оператора

«Действия → Производительность» содержит начало, отчёт и остановку замеров.
Те же команды: `/log perf start`, `/log perf`, `/log perf stop`. Кнопки
возвращают текст в существующее прокручиваемое окно результатов GUI.

Для CPU, event и journal очередей показываются текущие queued/in-flight
записи, пик outstanding, текущая и пиковая оценка данных, ограничения,
число начатых ожиданий, число ожидающих сейчас и максимум завершённых
ожиданий. Пики учитывают работу, уже переданную consumer, пока тот её не
завершил. Reset не скрывает уже удерживаемые данные. Если ожидание началось
до reset и завершилось после, максимум включает всю его длительность.

Чтение отчёта не создаёт worker, хранилище или соединение с базой. На горячем
пути добавлены примитивные максимумы под существующей блокировкой очереди;
форматирование и immutable snapshots создаются только при запросе отчёта.
Оценка данных не является полным размером объектов JVM. Один большой снимок
может обрабатываться отдельно и превысить обычный byte limit. Метрики не
заменяют измерение общего heap/GC, MSPT и времени клиентского кадра.

## Воспроизводимый синтетический тест

JDK 21, отдельный JVM-процесс, heap 128 MiB. Используется настоящий
WeightedQueue из исходников, без Minecraft, AuthCore и базы. Один producer,
один consumer, 20 000 операций прогрева, три раунда по 100 000 записей с
массивом 256 байт; проверяются порядок, данные и освобождение reservations.

Из корня репозитория:

```bash
mkdir -p build/queue-probe
javac -d build/queue-probe \
  src/main/java/com/roften/avilixlogger/core/ActionType.java \
  src/main/java/com/roften/avilixlogger/core/HotPathMetrics.java \
  src/main/java/com/roften/avilixlogger/core/WeightedQueue.java \
  tools/acceptance/QueueLoadProbe.java
java -Xms128m -Xmx128m -cp build/queue-probe \
  com.roften.avilixlogger.core.QueueLoadProbe > build/queue-load.json
```

Сохранённый результат: [queue-load-20261102.json](evidence/queue-load-20261102.json).
В трёх раундах p99 вызова put составил 5.689–11.157 мкс, максимум
0.236–1.262 мс. Это latency только handoff, без подготовки снимка, NBT,
дискового журнала, ClickHouse и клиентского интерфейса. Throughput producer
не объявляется пропускной способностью всего Logger. Allocation относится
к producer теста с созданием искусственного payload, не к удерживаемому heap
Logger. Результат не является A/B/A сравнением игры.

Контролируемый сценарий отдельно удерживает единственную reservation у
consumer на 100 мс. Второй put ожидает 100.348 мс; потерь и нарушения порядка
нет. Это воспроизводит сам риск блокировки producer, а не устраняет его.
Это исходный сценарий блокирующего worker put. После выбора политики
он больше не является серверным способом приёма. Для server offer есть
отдельные SERVER_CAPTURE_GUARD_OK и SERVER_CAPTURE_GUARD_NATIVE_OK проверки.

Нельзя обещать одновременно ограниченную память, отсутствие потерь и
отсутствие ожидания при бесконечно остановленном downstream. Поэтому отказ
от нового захвата сопровождается предупреждением и учётом интервала;
неограниченный буфер не введён. Нужны замеры реальной фермы/AE2/OPAC.
Штатная защита AuthCore сохранена; ключ передавать не требуется.
