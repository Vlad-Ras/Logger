# 2.1.35 — этап 8: долговечные границы записи

22 ноября 2026. Ветка `work/2.1.35-crash-recovery`. Разработка продолжается; отчёт не является выдачей релиза. Предыдущий этап: [зависимости от игроков](VERIFICATION_2.1.35_STAGE7.md).

## Изменения

Раньше выключение и повторное включение обработчика оставляло только поколение в памяти. После перезапуска оно не позволяло отличить непрерывную запись от периода с выключенным захватом. Для новых доказательств игрок ↔ блок добавлен отдельный файл мира `data/avilixlogger-capture.coverage`.

- Файл содержит UUID периода, SHA-256 сигнатуры настроек/версий модов, признак полноты и контрольную сумму. Пароли и другие credentials в него не записываются. Размер чтения ограничен 1 KiB, ссылки отвергаются.
- При изменении типов/обработчиков прежний период отзывается до публикации нового состояния. Config Loading/Reloading учитывает основной выключатель, флаги захвата и расположение/схему БД. Потеря подтверждённой авторизации и пауза из-за очереди тоже отзывают период. Повторное включение создаёт другой UUID.
- При безопасном новом запуске с теми же настройками/версиями сохраняется действующий UUID, поэтому сам перезапуск после краша не запрещает восстановление. Отсутствующий файл начинает новый период и не подтверждает прежние доказательства.
- Полнота намеренно консервативна: требуются включённые флаги захвата, группы и обработчики. Бит режима переполнения 30 не означает отключение типа событий и исключён из сигнатуры. Необязательные verbose-снимки не требуется включать.
- Запись выполняет отдельный daemon I/O worker: `.pending`, fsync файла и каталога, атомарная замена, повторный fsync каталога. Вызывающий код ждёт долговечности на границе настройки/сбоя. Действие инвентаря не записывает файл; читает volatile UUID. Worker покрытия отделён от worker WAL во избежание взаимного ожидания.
- Целая pending-запись после падения принимается при старте до проверки настроек. Повреждённая метка не считается разрешением. Ошибка публикации блокирует выдачу новых меток и проверку сцены; выполняется удаление прежнего разрешения с fsync каталога. Если сам накопитель отвергает и запись, и удаление/fsync, долговечность гарантировать невозможно.
- Новый envelope переноса имеет Format 2 и UUID Coverage до/после. Старые proof-envelope без метки отвергаются при подготовке; старые события не получают подтверждение задним числом. Сигнатура строится по прямым ссылкам на конфигурацию, без зависимости от имён полей после обфускации.
- Координатор проверяет файл до чтения доказательств из БД. Поколение отслеживает изменения во время сцены до мутаций/завершения; финальный worker повторяет проверку истории/метки для активного игрока. Переключение после начала применения вызывает компенсацию.

## Проверки

Java 21, NeoForge 21.1.265. Компонентные проверки `testAsyncPipeline verifyMixinSafety verifyObfuscatedJar testCreatePreflight` прошли. `CAPTURE_COVERAGE_OK` включает реальную файловую запись, безопасный restart, отзыв/включение, неполную конфигурацию, отказ авторизации, смену сигнатуры, отсутствующий/повреждённый файл, ссылки, pending и ошибку записи. Отдельная дочерняя JVM делает `Runtime.halt(73)` после долговечного отзыва; новый процесс не оживляет старое доказательство.

В native-сцене без Create прошли `PLAYER_COVERAGE_NATIVE_OK`, `PLAYER_TRANSFER_NATIVE_OK` и GC-проверка 1 MiB. Выключение/включение типа во время preflight отвергается до мутаций; переключение обработчика после WAL возвращает исходное содержимое блока и освобождает резервы. PUT/TAKE, preview, повтор, онлайн/офлайн, конфликт и выход игрока также прошли.

Итоговый прогон с Create прошёл: `PLAYER_COVERAGE_NATIVE_OK`, `PLAYER_TRANSFER_NATIVE_OK`, `PLAYER_TRANSFER_MEMORY_RELEASE_OK`, `BUILD SUCCESSFUL`. Логи — `build/coverage-final/`. Заново прошли четыре JVM игрока с двумя `Runtime.halt(73)`: `PLAYER_MULTIPROCESS_OK`, точная стартовая компенсация и отказ повторной выдачи после commit; файл офлайн-игрока неизменен. Логи — `build/coverage-player-restarts/`. Native-компоненты запускаются через тестовые точки входа, с явными fixture UUID доказательств. Они не разрешают штатную авторизацию Logger и не заменяют проверку лицензированной сборки.

## Что это не закрывает

Метка подтверждает обработанные Logger границы настройки/авторизации/очереди. Она не доказывает работу отсутствующего модового адаптера, сессию сервера с полностью удалённым Logger, внешнее редактирование мира/БД или произвольную замену файлов мира. Ещё нужна связь с другими путями изменения мира, включая обычные/Create-откаты, подавляющие повторный capture. Для таких случаев проверка происхождения/покрытия истории остаётся открытой; универсальная гарантия всех распределённых ресурсов не заявляется.

Открыты запись инвентарей игроков, производственные преобразования, жидкости/энергия, непрозрачные модовые ресурсы и полная матрица сборки. По-прежнему нужны актуальный модпак/конфиги, положительная штатная авторизация, живой обфусцированный Logger и окончательные сеть/TPS/FPS/RAM до выдачи JAR.
