# 2.1.35 — этап 9: связь между режимами восстановления

22 ноября 2026. Ветка `work/2.1.35-crash-recovery`. Разработка, не выдача релиза. Предыдущий этап: [долговечные периоды записи](VERIFICATION_2.1.35_STAGE8.md).

## Исправленная граница

Обычный откат или восстановление Create могут намеренно изменить контейнер, не создавая повторных capture-событий. Старое доказательство игрок ↔ блок после этого нельзя использовать как подтверждение утраченного переноса. Добавлен общий отзыв периода перед входом в `CartAuditContext.restoring(true)`.

- Первый вход отзывает метку с fsync до выполнения native-мутации. Вложенные входы и следующие порции одной операции не записывают метку повторно.
- Пока операция активна, смена конфигурации/авторизации не открывает выдачу новых доказательств. Обновление метки выполняется в конце серверного тика после координаторов, когда нет активного обычного/аварийного/Create-отката и текущего restoring-контекста. Новый период имеет другой UUID.
- После успешного долговечного отзыва последующая ошибка обновления метаданных не запрещает завершить/компенсировать уже защищённую операцию. Если не удалось выполнить самый первый отзыв, первая native-мутация не разрешается. Новая выдача proof при ошибке остаётся заблокированной.
- Явный отзыв добавлен перед выдачей восстановленной штуковины в предмет, выдачей рюкзака и удалением исходного рюкзака при административном переносе.
- Чистые detached-кодеки `CartRecoveryContents.validate` и `CartStateReplay` используют отдельный контекст подавления: их данные не содержат ссылок на мир/игрока. Предпросмотр не отзывает историю только из-за проверки кодека.
- Пустой `CartRollbackCoordinator.stop()` больше не входит в restoring: обычное завершение сервера без активного отката само по себе не отзывает доказательства.
- Проверка восстановления по-прежнему консервативна: отзыв глобальный для новых player/block proof, без попытки угадать, затронула ли другая операция именно этот перенос. Уже начатая, но отменённая обычная/Create-операция тоже может отозвать старый период.

## Аварийная сцена с WAL

Применение и компенсация общей сцены используют отдельный package-private restoring-контекст. До commit их точный результат защищён долговечным undo-журналом, поэтому сама запись NBT каждого блока не отзывает доказательства сцены.

Порядок завершения: повторная проверка → flush мира → долговечный отзыв периода → commit/квитанция WAL → освобождение резервов. Так завершённая аварийная сцена тоже не оставляет пригодными посторонние старые доказательства. Отказ записи метки до commit позволяет компенсировать мир из существующего WAL. Ошибка после публикации commit сохраняет прежнее правило карантина.

Стартовая компенсация незавершённого WAL не создаёт внешнюю мутацию периода. Если авария произошла после отзыва, но до commit, мир возвращается назад, а прежние proof остаются отозванными. В таком случае автоматическое повторное использование старого доказательства намеренно запрещено, даже если блоки удалось вернуть точно.

Сигнатура proof-schema повышена до `player-block-coverage-2`: старые периоды кандидата этапа 8 не принимаются как подтверждение новой границы. Форматы `.scene`, квитанций и envelope Format 2 не изменялись.

## Проверки

Среда: Java 21, NeoForge 21.1.265. Пройдены `testAsyncPipeline verifyMixinSafety verifyObfuscatedJar testCreatePreflight`.

| Проверка | Подтверждённый результат |
|---|---|
| `CAPTURE_MUTATION_OK` | Journal/detached-контексты сохраняют метку; обычный restoring отзывает её; вложенность/cleanup, отсутствие повторной записи на 10 000 порций, запрет возобновления через настройки, busy/idle settlement, продолжение уже защищённого restoring-контекста после поздней ошибки метаданных и отдельная JVM с `halt(73)` |
| Native без Create/Ponder/Flywheel | Реальный откат контейнера с 5 алмазами до пустого состояния отзывает старую метку; preview и точная WAL-отмена её сохраняют; commit отзывает; ошибка метки приводит к компенсации |
| Native с Create | Те же проверки плюс реальный вызов detached-кодека Create; изменение мира в общем restoring-контексте отзывает метку |
| Player-регрессии с/без Create | PUT/TAKE, preview, конфликт, подключение/выход, online/offline, квитанции и GC 1 MiB прошли |
| Полный Create smoke | `AVILIX_CREATE_SMOKE_OK`: упаковка/сохранение/загрузка, detached/incremental, груз/жидкости, commit/cancel, получатели, native-меню, дроп и конфликты; 8 MiB резервный снимок освобождается |

Заново прошли многопроцессные сценарии: девять JVM блоков/сущностей с пятью авариями (`RECOVERY_MULTIPROCESS_OK`), четыре JVM игрока с двумя авариями (`PLAYER_MULTIPROCESS_OK`), две JVM новой commit-границы с одной аварией (`MUTATION_FENCE_MULTIPROCESS_OK`). В последнем случае сохранённый мир точно отменён после отзыва метки перед commit; старое доказательство не оживает после включения. Логи — `build/mutation-scene-restarts`, `build/mutation-player-restarts`, `build/mutation-fence-restarts`, общий итог — `build/mutation-final/`. Скрипт новой границы — `tools/ci/verify-mutation-restarts.py`; мир всегда создаётся в отдельном временном каталоге.

После уточнения обработки поздней ошибки метаданных повторены компонентный/obfuscation/mixin/preflight-набор и native-проверки с Create, включая пустой shutdown: `build/mutation-final/checks-last.log`, `native-last.log`; оба запуска успешны.

Native-проверка метаданных использует отдельный fixture Ledger и явные UUID proof, не меняет AuthCoreBridge и не разрешает штатную авторизацию Logger. Результат проверки компонентов не является положительной приёмкой лицензированного обфусцированного JAR на сервере пользователя.

## Открытые условия выпуска

Этот этап связывает собственные обычные/Create-откаты и административную выдачу с отзывом новых player/block proof. Он не подтверждает незаписанные изменения сторонних команд/адаптеров, внешнюю правку мира/БД, запуск сервера вообще без Logger или произвольную подмену файлов.

Остаются запись инвентарей игроков, производственные преобразования, жидкости/энергия и непрозрачные модовые ресурсы, полная матрица актуальной сборки, положительная штатная авторизация и финальные сеть/TPS/FPS/RAM. Финальный JAR по этому отчёту не выдаётся.
