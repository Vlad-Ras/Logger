# AvilixLogger 2.1.29: владельцы, время и задержки

Сборка объединяет историю `work/2.1.26-storage-gui-20261102` (169aa6f) и `work/2.2.0` (8590692), а не заменяет одну из веток старой копией. Включены предыдущие исправления смертей/Corpse, перехода к записи, форм времени и переключателей Create.

## Поведение

- Поиск «От» и ограниченный диапазон идут по `ts_ms ASC, id ASC`, начиная с указанного времени. «До» и обычная история сохраняют обратный порядок. Составной курсор учитывает одинаковые метки времени и ID, выданные при корректировке часов. Фильтрация выполняется до LIMIT в БД.
- Точная выбранная запись и выделение читаются по exact ID / IN ID, без подмены соседней строкой и обхода тысяч соседних NBT.
- Страница истории штуковин читает заголовки без полного NBT. Снимок старой строки без нового маркера проверяется при восстановлении. Кнопки восстановления доступны по прежним правам.
- История имеет отдельные два потока и очередь из 16 запросов. Она не ждёт единственную очередь подготовки откатов.
- Ожидание видимости ограничено уже принятым префиксом записей. Новые события не продлевают его бесконечно. Учитываются работа CPU в полёте, сброс агрегации, подтверждение ClickHouse, журнал прошлого процесса и изменение системных часов.
- Выбранный исторический снимок возвращения штуковины не ожидает всех текущих событий. Получение последнего состояния сохраняет ожидание подтверждённой истории. Резервации и защита от повторной выдачи сохранены.

## Аудит источников

| Обработчики | Основание для игрока | Системные случаи |
|---|---|---|
| Активатор: действие, блок, удар, инвентарь, барьер ошибки захвата | Явный владелец активатора, затем известный владелец штуковины | Неизвестный владелец |
| Бур, пила, уборка, плуг, каток и другие исполняющиеся акторы | Текущий механизм и тот же ID штуковины; известный владелец | Нет текущего механизма или владельца |
| Груз, storage_io и общий манифест передачи | Тот же подтверждённый контекст; реальный установленный игрок сохраняется | Обычная автономная передача без такого контекста |
| Подбор/выбрасывание, меню, AE2, контейнеры, рюкзаки, изменения экипировки и текста | Игрок из непосредственного вызова; существующая проверка технического игрока | Нет доказанного инициатора |
| Отложенный снаряд Create | Сохранённый при создании источник и владелец | Источник неизвестен |
| Загрузка/удаление предмета, жизненный цикл поезда, загрузка трупа | Только отдельный подтверждённый вызов игрока | Сам факт загрузки не является действием владельца |
| Curios/Accessories: наблюдение в тике | Непосредственные операции логируются отдельно | Носитель является целью, а не доказанным инициатором прошлого изменения |
| OPAC: асинхронный successful-action | Явные входные действия логируются отдельно | performedAs — техническая роль; хранится в деталях |

Произвольное соседство с игроком и история владения не используются для подмены причин. Старые сохранённые SYSTEM-записи не переписываются.

## Create и память

В присланных Observable-профилях есть цепочки ItemEntity/Create → обработчики Logger → ItemStack.save/NbtUtils.writeBlockState/Field.get. Обычные внешние операции Create теперь откладывают построение дескриптора и NBT до появления подтверждённого участника-штуковины или специального creative IO. Несвязанный callback освобождает временные копии без сериализации. Контракты классов кэшируются через ClassValue, двойной сундук читается через существующий accessor. Доступ к живому миру остаётся на серверном потоке, а работа с отделёнными данными — в фоновых обработчиках.

Очереди учитывают байты и обрабатываемые элементы. Новая таблица inFlight содержит только незавершённые работы и освобождается после complete. Временные внешние изменения ограничены 512 элементами на операцию; страницы — бюджетом 8 MiB и ограниченным числом запросов. Дисковый backlog не загружается целиком в heap. Эти пределы относятся к учитываемым данным, а не ко всему heap JVM; один сверхбольшой снимок обрабатывается отдельно.

Переключатели механизмов Create добавлены как ID 31–40, чтобы сохранить существующие ID 1–30 из 2.1.28. Маска расширена до long, старые численные значения сохраняются. Полные снимки конструкции/содержимого и lifecycle продолжают работать при отключении подробного логирования. Неполная история получает барьер: откат отдельных действий через незаписанный промежуток запрещён, восстановление сохранённого полного снимка доступно.

Сетевой протокол 11: обновить мод и на сервере, и на административном клиенте.

## Границы проверки

Проверены сборка, настоящий ClickHouse и игровые callback. Количественные результаты и ограничения приведены ниже. Синтетическая очередь не является замером Minecraft TPS; запуск игровых проверок не является длительным профилем полного серверного модпака. Для утверждений об итоговых TPS и RAM живого сервера требуется одинаковый Spark/JFR сценарий до/после на нём.

## Измерение несвязанной автоматики Create

Финальная сборка, профиль logged-pack (Create 6.0.10 / AE2 19.2.18 / Backpacked 3.0.0-beta.15): настоящий серверный callback, настоящий InvWrapper сундука, source Create chute, 1000 прогревочных + 5000 операций. Положительный контроль из 100 вызовов прежнего дескриптора дал 100 срабатываний счётчика. В измеряемом новом пути: дескрипторов 0, вызовов снимков NBT 0, CPU 23,989 мс суммарно (4,798 мкс/операцию), wall 24,088 мс; выделено 9 570 608 байт (около 1914 байт/операцию). Это выделения, а не удерживаемый heap. Создание ItemStack и снимки входных значений включены; полноценный путь записи при положительном AuthCore и полный модпак не включены.

Проверка фиксирует отсутствие ненужного чтения метаданных/NBT в конкретном callback и стоимость этого пути. Она не является заявлением «логгер не влияет на TPS» или сравнением полного сервера с 2.1.28. JFR всех игровых проверок также включает сборку/откат сотен искусственных конструкций и создание технических игроков; его агрегаты не подменяют steady-state профиль живого сервера.

Исходные количественные данные: [очередь](evidence/2.1.29/queue-probe.json), [Create](evidence/2.1.29/create-automation-cost.json).

Для прозрачности сохранена [сводка JFR полного набора игровых фикстур](evidence/2.1.29/jfr-fixture-summary.json): последний heap после GC около 3,04 GiB за 110 с прогона. Это память всего тестового игрового процесса после сотен специальных сценариев, не размер очередей и не оценка обычного сервера. По такому короткому прогону нельзя заключить отсутствие долговременной утечки или назвать расход RAM производственного сервера.
