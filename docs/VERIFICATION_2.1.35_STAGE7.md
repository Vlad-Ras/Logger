# 2.1.35 — этап 7: зависимости от инвентарей игроков

Дата: 22 ноября 2026. Ветка: `work/2.1.35-crash-recovery`. Это отчёт разработки, не приёмка релиза. Предыдущие результаты: [этап 6](VERIFICATION_2.1.35_STAGE6.md).

## Что реализовано

Аварийное восстановление теперь может учитывать подтверждённый перенос между игроком и ванильным контейнером, не изменяя инвентарь игрока. Например: игрок положил 7 предметов, его пустой инвентарь уже сохранился, а чанк сохранился до переноса. Связанные снимки позволяют восстановить эти 7 предметов в блоке. Обратное направление тоже проверено. Несовпадение текущего игрока с подтверждённым конечным состоянием вызывает отказ.

- Снимки снимаются вокруг штатного вызова меню: 41 слот игрока, предмет на курсоре, полное состояние контейнера, общий UUID переноса и результат native-вызова. Сравнение и баланс выполняются на worker по отсоединённым данным. Исключение не превращается в успешное доказательство.
- Поддержаны точные штатные классы ChestMenu, HopperMenu, DispenserMenu, ShulkerBoxMenu и соответствующие ванильные chest/trapped chest/barrel/hopper/dispenser/dropper/shulker box. Модовые подклассы и FakePlayer этим правилом не разрешаются.
- Восстановление считает только переносы между текущей контрольной точкой блока и его целью. Внешняя дельта игрока дополняет общий предметный баланс сцены. Цепочка состояний игрока должна быть непрерывной; конечный курсор — пустым.
- Для онлайн-игрока резервируются UUID, объект, инвентарь и меню; состояние повторно проверяется до мутаций и перед завершением. Обычная начальная загрузка инвентаря при входе не блокируется; смена подключения во время сцены отвергается.
- Для офлайн-игрока читается штатный `.dat` вне Server thread: точные UUID/DataVersion, ограничение размера/NBT, запрет ссылок и повторных слотов, корректное сопоставление брони/второй руки. Файл перечитывается перед завершением. Сцена не записывает этот файл.
- Связанные строки повторно читаются по точным ID и SHA-256 значимых полей. Проверяются последующие изменения блоков и известные CAPTURE_GAP без фильтра по игроку. Идентичные дубликаты строк допустимы, противоречивые — нет.
- ID использованных переносов, включая подтверждённые no-op, входят в существующий WAL/commit/квитанцию. Формат журнала v2 не менялся. Повторная выдача уже подтверждённого переноса запрещена после нового запуска JVM.
- Исправлено отбрасывание цепочки A → B → A: если на диске остался B, одинаковые первый/последний снимки не означают отсутствие работы.
- В таблицу BLOCKS добавлены четыре поля снимков контейнера/игрока с аддитивной миграцией, INSERT и SELECT. Доказательства переноса сохраняются даже при отключённых необязательных rollback details.

## Выполненные проверки

Среда: Java 21, NeoForge 21.1.265, существующий локальный Create runtime. Все следующие проверки завершились с ожидаемыми маркерами; один только код возврата Gradle не считался подтверждением native-теста.

| Проверка | Результат |
|---|---|
| `testAsyncPipeline verifyMixinSafety verifyObfuscatedJar testCreatePreflight` | Успех; `PLAYER_BLOCK_TRANSFER_OK`, `PLAYER_TRANSFER_HTTP_OK` |
| Реальный shift-click, PUT/TAKE, предпросмотр и повтор | Успех: блок исправляется, игрок остаётся неизменным; preview не создаёт WAL/мутаций |
| Конфликт, поздняя история, защита/отмена, подключение/выход | Успех; реальный PlayerList.remove отвергается до изменения сцены, позднее прямое изменение инвентаря вызывает компенсацию |
| Штатные сохранённые данные офлайн-игрока | PUT/TAKE прошли; содержимое файла не изменяется |
| Четыре отдельные JVM, два `Runtime.halt(73)` | `PLAYER_MULTIPROCESS_OK`: незавершённая операция отменяется; после commit повтор запрещён; SHA-256 player `.dat` сохраняется |
| Без Create/Ponder/Flywheel | `PLAYER_TRANSFER_NATIVE_OK`; общая защита игрока работает без Create |
| Итоговые три свежих мира с Create | `PLAYER_TRANSFER_NATIVE_OK`, `CRASH_RECOVERY_NATIVE_OK`, `ENTITY_RECOVERY_NATIVE_OK`; все три Gradle-запуска успешны |
| Освобождение снимка | `PLAYER_TRANSFER_MEMORY_RELEASE_OK`: отсоединённый NBT с 1 MiB custom data собирается GC после commit |

Локальные воспроизводимые сценарии: `PlayerBlockTransferTest`, `PlayerTransferNativeSmoke`, `tools/ci/verify-player-recovery-restarts.py`. Итоговые логи: `build/player-regression-final/{players,scene,entities}.log`, `build/player-recovery-restarts/`, `../player-stage-components-final.log`, `../player-stage-no-create.log`. Логи/миры не включены в git.

Native-сценарии вызывают проверяемые компоненты через тестовые точки входа. В этих прогонах штатная авторизация Logger недоступна; это не положительная проверка лицензированной работы всего мода. Предыдущая проверка настоящего обфусцированного AuthCore подтверждала загрузку API и отказ без ключа, не успешную авторизацию.

## Нагрузка и пределы измерений

| Путь | Наблюдение | Ограничение |
|---|---|---|
| Server thread | 200 пар дополнительных снимков, 41 заполненный слот, 4 KiB custom data: среднее 0,0731 мс/пару с Create, 0,1022 мс без Create | Это локальный микрозамер снимков; не MSPT сервера с онлайном и не полная стоимость логирования |

| Сеть/БД | HTTP-тест проверяет обязательное сохранение и чтение четырёх полей, даже при отключённых optional details | Объём строк увеличился; задержки настоящего ClickHouse и суммарный трафик под онлайном не измерены |
| Клиент/FPS/GUI | Новых клиентских экранов, виджетов и форматов пакетов здесь нет; добавлена серверная фаза прогресса | Массовый replay и полный клиентский модпак повторно не профилировались; прежние замеры этапа 5 не заменяют это |

## Оставшиеся условия выпуска

1. Игрок здесь — участник только для чтения. Изменение его инвентаря, модовые attachments, производственные преобразования, жидкости/энергия и непрозрачные хранилища ещё не реализованы этим этапом.
2. Известные CAPTURE_GAP и текущая пауза проверяются, но отсутствие gap не доказывает непрерывную запись при намеренном выключении и последующем включении отдельных обработчиков. Нужна долговечная проверка покрытия истории. Универсальная гарантия отсутствия дюпа при незаписанных действиях пока отсутствует; это блокирует финальный выпуск.
3. Старые строки без связанных снимков игрока нельзя задним числом превратить в доказательство переноса.
4. Нужны актуальные модпак/конфиги, положительная штатная авторизация, проверка обфусцированного Logger на этой сборке и окончательные сеть/TPS/FPS/RAM. Предоставлен исходный AuthCore, актуальная серверная сборка пока не получена.

Девятипроцессный сценарий этапа 6 с пятью авариями остаётся отдельным ранее полученным результатом; в этом проходе заново выполнены четыре JVM для игрока и три итоговых native-регрессии. Кандидат не выдаётся как готовый релиз.
