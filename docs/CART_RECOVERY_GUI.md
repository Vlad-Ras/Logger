# Восстановление вагонеточной штуковины и отдельная GUI

Статус: изменения исходников поверх 2.1.19, ещё не выпущенный патч. Не установлено на сервер пользователя. Полная компиляция, проверка GUI в игре и нативные тесты заблокированы отсутствием Gradle/JDK21/бинарных зависимостей в текущей среде. Нельзя выдавать этот статус за готовый JAR.

## Проблема версии 2.1.19

`/log cart rollback <UUID> <entry>` готовит откат периода: может возвращать блоки мира, груз и связанные инвентари, а не просто выдавать штуковину. При отсутствии текущей конструкции/предмета этот путь обычно отказывает. В версии 2.1.19 отдельной команды восстановления пропавшей штуковины в предмет нет.

## Новый порядок

1. Установить проверенный патч на сервер и клиент. Новый отдельный экран использует сетевой протокол 5. Старый клиент с протоколом 4 для нового GUI не подходит; игроки без клиентской части используют чат-команды.
2. `/log cart` открывает отдельную страницу вагонеточных штуковин. Пустое поле ID показывает общую историю; вставьте UUID и нажмите «Найти» для одной штуковины. `/log cart history <UUID>` сразу открывает её страницу. `/log cart find <ник>` остаётся поиском по действиям игрока; кнопка `[ID]` копирует UUID, текст строки открывает историю.
3. Выбрать строку: справа показываются дата, игрок, координаты, формы до/после, сохранённый снимок и явный `entry`. Кнопки `ID`, `entry`, `JSON` копируют данные в буфер. JSON запрашивается отдельно по выбранной строке.
4. Для пропавшей штуковины: **«Выбранный снимок → предмет»** либо **«Последний снимок → предмет»**. Предпросмотр указывает точные UUID, entry, сторону до/после, время, число блоков и получателя. Восстановление выдаёт предмет в свободный слот администратора. Действия в мире не откатываются.
5. **«Откат действий к строке»** запускает существующий отдельный предпросмотр периода. Он показывает число затрагиваемых блоков и слотов. Для выдачи исчезнувшей штуковины эта операция не нужна.
6. Подтверждение привязано к UUID и entry. При смене предпросмотра старое подтверждение не может применить другой снимок.

Чат без клиентской части:

- `/log cart chat <UUID> [before]` — страницы по 8 строк, явный entry и копируемый UUID.
- `/log cart recover <UUID> latest` — предпросмотр последнего доступного полного снимка.
- `/log cart recover <UUID> <entry>` — снимок строго из указанной записи.
- `/log cart confirm-recovery <UUID> <entry>` — выдача после предпросмотра (2 минуты).
- `/log cart cancel-recovery` — отмена предпросмотра.

## Что сохраняется и ограничения

- Из Form=item берётся штатный предмет с компонентами. Из Form=entity берётся сохранённый `Entity.Contraption` и исходное направление; тип предмета выбирается по базовой обычной/печной/сундуковой вагонетке. Удаляются только UUID/Pos/Motion корня payload, как при native упаковке Create. Сохранённые блоки, BE-данные, акторы, mounted item/fluid storage передаются целиком.
- При удалении полный снимок обычно находится **до** события: recovery смотрит после, затем до. Sparse запись позиции/статуса не превращается в полный снимок.
- «Последний» означает последний **полный сохранённый снимок**, а не реконструкцию на последнюю миллисекунду перед крашем. Более поздние отдельные изменения груза/блоков не воспроизводятся и действия мира не откатываются. Если нужного состояния нет в журнале, его нельзя обещать восстановить.
- Сцепки, вложенные конструкции и непустой инвентарь самой базовой сундуковой вагонетки отклоняются, чтобы упаковка не потеряла внешнее состояние. Mounted-сундуки внутри конструкции сохраняются.
- Проверяются загруженная конструкция/дроп и онлайн-инвентари, эндэр-сундуки и курсоры. Офлайн-инвентари и произвольные выгруженные хранилища не просматриваются. Предпросмотр просит администратора подтвердить фактическую утрату.
- До выдачи записывается однократный файловый резерв UUID в `data/avilix-cart-recovery/<UUID>.nbt` через CREATE_NEW/force. Повторная выдача того же ID, включая иной entry, блокируется. Неудача после резерва требует ручной проверки администратором; автоматической повторной выдачи нет. При последующей новой утрате этого ID резерв также требует ручной проверки. Откат самой файловой системы может откатить и резерв.
- SQL, чтение/разбор/подготовка снимков, декодирование предмета, проверка native лимита и запись резерва выполняются в ограниченных рабочих очередях. На серверном потоке остаются проверки актуального состояния, просмотр онлайн-инвентарей по запросу администратора и выдача в один слот. Нулевую нагрузку или нагрузочные показатели без замера не заявляем.
- В журнале выдача записывается как CART_ROLLBACK с фазой `recover_item`, entry/side и `world_changes=0`, без изменения прежних номеров действий. Прежний откат действий остаётся отдельным путём.

## Проверки

Добавлен CartRecoveryPlanTest: строго выбранная/последняя запись, состояние перед удалением, неизменность исходного NBT, сохранность грузового payload, отказы для чужого ID/пустого снимка/неподдерживаемого типа/вложенности. В native CreateCartSmoke добавлено сравнение результата с штатной упаковкой Create и возврат блоков, 12 алмазов и 1250 mB воды. Эти новые тесты ещё не выполнены.

Синтаксический разбор изменённых Java-файлов и diff проверяются отдельно; это не компиляция, не проверка типов и не проверка отображения GUI.

Результат проверки 18.10.2026: syntax-only разбор 15 изменённых/новых Java-файлов в каждой ветке — 0 ошибок; diff и отсутствие конфликтных маркеров проверены. `./gradlew testAsyncPipeline compileCreateSmokeJava --offline` не дошёл до компиляции: Gradle 8.14 отсутствует, загрузка завершилась `Network is unreachable`. Функциональные тесты, отображение GUI, производительность и выпуск JAR остаются непроверенными. Версия мода не повышалась.
