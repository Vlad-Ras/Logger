# 2.1.35 — этап 10 и тестовый JAR

22 ноября 2026. Minecraft 1.21.1, Java 21, NeoForge 21.1.265, Create 6.0.10, AE2 19.2.12. Ветка `work/2.1.35-crash-recovery`. Выдаётся тестовый кандидат, не финальный выпуск. Полный список изменений относительно 2.1.34: [CANDIDATE_2.1.35.md](CANDIDATE_2.1.35.md).

## Обычные баки Create

Добавлен отдельный баланс жидкости аварийной сцены по полным штатным NBT: `TankContent.Fluid` с точными ID, количеством и компонентами. Проверка выполняется на worker без ссылок на мир; настройки ёмкости на блок и максимальной высоты снимаются на серверном потоке. Жидкость контроллера многоблочной ёмкости учитывается один раз. Проверяются все части, их координаты/контроллер, форма, ёмкость и отсутствие незавершённого объединения.

Контроллер вне сцены определяется до разрешения общей capability: дочерняя часть не вызывает скрытую загрузку контроллера за пределами подготовленной области. Если неизменявшаяся часть отсутствует в истории периода, координатор включает её как неизменяемую зависимость по текущему полному снимку; это допускается только внутри выбранных администратором границ. Снимок прошлого для такой части не выдумывается. Форма текущего и целевого резервуаров должна пройти проверку целиком.

Сцена с замкнутым переносом сохраняет общий запас жидкости. Смешанное сохранение с неподтверждённым изменением общего объёма отвергается до WAL/изменений. Для креативных баков и активных котлов нужны отдельные ресурсные контракты; они не выдаются за обычные баки. Причины отказа имеют стабильный код, русское пояснение и координаты.

## Выполнено

- `testAsyncPipeline verifyMixinSafety verifyObfuscatedJar testCreatePreflight` прошли, включая `RECOVERY_FLUID_BALANCE_OK`: полные многоблоки, переносы, форма, алиасы, компоненты, повреждённые данные, ограничения памяти и отмена.
- Native `FLUID_RECOVERY_NATIVE_OK`: реальный двухблочный бак и второй бак в другом чанке, 4000 мБ → 1000/3000 мБ; preview, commit/repeat, отмена до/после частичного применения, блокировка старой/дочерней capability, отказ смешанного сохранения и неполной области.
- Дополнительный native-проход проверил автоматическое включение неизменявшейся части, отсутствующей среди исторических целей; она сохраняется без изменения. Дочерняя часть без контроллера в сцене отвергается.
- Две отдельные JVM: `FLUID_MULTIPROCESS_OK`. Принудительный `Runtime.halt(77)` после сохранения частичного обновления (1000/0 вместо исходных 4000/0); при новом запуске производственный WAL вернул ровно 4000/0 и общий контроллер до игровых тиков.
- Общий Create smoke: `AVILIX_CREATE_SMOKE_OK`; повторены проверки без Create (`PLAYER_TRANSFER_NATIVE_OK`). Резервный NBT 8 MiB и связанный снимок игрока 1 MiB после завершения собираются GC.
- Реальный клиент: `CART_GUI_CLIENT_OK`, `RECOVERY_GUI_NATIVE_OK`, `SERVER_LOG_GUI_NATIVE_OK`, `SERVER_LOG_FOLDER_OPEN_NATIVE_OK`. Проверены общие виджеты и три размера: 320×240, 640×360, 960×540. Снимки формы восстановления и меню логов просмотрены.
- Кнопка открытия папки нажата через native GUI; тестовый Linux `xdg-open` записал точный URI клиентского каталога. Это не проверка Windows Explorer. Диагностический файл сохранился в правильной подпапке с точными байтами.

Логи: `../fluid-candidate-build.log`, `build/fluid-final/{fluids,fluid-auto,no-create,create-full,build-last}.log`, `build/fluid-recovery-restarts/`, `build/fluid-client/client.log`. Скрипт перезапусков: `tools/ci/verify-fluid-restarts.py`. Миры тестов отдельные, под `build/`.

Native-тесты компонентов и GUI не разрешают AuthCoreBridge. Положительная штатная авторизация итогового обфусцированного JAR на сборке пользователя не проверена; проверка AuthCore не отключалась в поставляемом коде.
