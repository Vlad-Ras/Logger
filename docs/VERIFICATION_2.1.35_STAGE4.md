# AvilixLogger 2.1.35 — этап 4: сущности и повторные аварии

Дата: 21 ноября 2026. База: 2.1.34. Ветка: `work/2.1.35-crash-recovery`. Это отчёт разработки, не разрешение на выпуск.

## Реализация

Жизненный цикл replay читается вперёд вместе с блоками: появление создаёт целевое состояние, удаление задаёт отсутствие. Появление с последующим удалением не превращается в воскресшую сущность. Фильтр не может оставить половину цепочки. Дерево пассажиров ограничено 256 узлами и глубиной 32; UUID должны быть уникальны, игроки запрещены. Совместные записи появления пассажиров объединяются только при одинаковой авторитетной группе и точном совпадении NBT.

Поиск сохранённых UUID выполняется вне Server thread во всех измерениях через очередь `SimpleRegionStorage`/`IOWorker`. Заголовки регионов, ошибки чтения и повторные местоположения проверяются; нулевой файл пустого региона допустим, занятый нечитаемый чанк не считается доказательством отсутствия. Предел поиска — две минуты и миллион занятых чанков на измерение. Глобальная проверка свежести истории ограничена 100 000 событиями; это защитные ограничения, а не обещание мгновенной проверки большого мира.

Блоковые чанки FULL не гарантируют загрузку сущностей. Удержание сцены явно ставит их в штатную очередь загрузки без изменения видимости. Сохранение скрытой секции сохраняет данные, но не выгружает зарезервированные UUID. Сущности и блоки используют общую компенсацию и общий журнал до первой мутации. Изменение измерения не принимается как локальное совпадение NBT.

Журнал версии 2 содержит точные before/after деревья сущностей и положительные ID событий; версия 1 остаётся читаемой. После сохранения результата `.scene` атомарно переименовывается в `.committed`, затем создаётся малая `.receipt`. Если публикация квитанции прерывается, новый старт завершает её по полному committed-файлу. Незавершённая сцена компенсируется; завершённое событие не выдаётся ещё раз даже после ручного удаления сущности.

Квитанции не удаляются автоматически. Это защищает от повторной выдачи, но требует будущей стратегии компактного хранения большого числа завершённых событий; сейчас действует ограничение миллиона ключей с явным отказом при превышении.

## Начальное покрытие

- Marker и display: создание без ресурсного переноса; удаление одного такого корня допускается при полном совпадении живого состояния.
- Корова, свинья, овца, курица, стойка для брони, лодка, обычная вагонетка: создание требует доказательства `/summon` либо подходящего vanilla-предмета в creative. Доказательство фиксируется производителем события на серверном потоке, а не угадывается по тексту строки.
- Вагонетка с установленным Create требует его структурного участника: обычный NBT не включает внешний реестр контроллера. Generic replay отказывает до мутаций. Стандартный отдельный режим Create не удалён.
- Контейнерные сущности, ресурсные смерти, поводки, команды/счета scoreboard и неизвестные модовые attachments/persistent data требуют полных связанных участников. Они пока не восстанавливаются новым generic replay. Точный пустой sentinel `create:minecart_controller={Type:"EMPTY"}` у не-вагонетки сохраняется; дополнительные неизвестные поля отвергаются.
- Уже существующий UUID с подходящим полным деревом сохраняет текущий NBT и положение. Неполное дерево, чужой транспорт, одинаковый UUID в нескольких местах, более поздняя история и конфликт данных останавливают всю сцену.

Это частичное покрытие пункта сущностей. Наличие класса или общего сериализатора не означает совместимость со всеми модами.

## Проверки

Успешный native-сценарий `ENTITY_RECOVERY_NATIVE_OK` проверяет совместную отмену блока и сущности, освобождение резервирования, долговечный запрет повторной выдачи, отказ неподтверждённого survival-создания до изменения блока, отказ неподключённого контроллера Create, точное создание коровы/стойки/лодки, отсутствие дропа при уроне/kill во время сцены, общую группу пассажиров, UUID в выгруженном чанке и saveAll скрытой секции.

Многопроцессный запуск: `python3 tools/ci/verify-recovery-restarts.py`. Тест требует маркеры и конкретные коды `Runtime.halt`, поскольку Minecraft может завершить Gradle с кодом 0 даже после ошибки в ServerStartedEvent. Все инъекции аварий находятся в `src/createSmoke`; в production JAR они не должны попадать.

Итог остальных прогонов дополняется после завершения; ни сценарий в исходниках, ни `BUILD SUCCESSFUL` сами по себе не считаются приёмкой.

## Интерфейс и диагностика

`/log replay details [страница]` показывает по 12 причин из текущего предпросмотра: ID записи, измерение, координаты, UUID и объяснение. Используется тот же ограниченный кеш плана; новые NBT и выборка истории не создаются. Доступ — существующее административное право. Кнопка добавлена в общий `LoggerActionCatalog`, экран использует существующие компоненты.

Предпросмотр явно обозначает количества как верхнюю оценку по журналу до проверки мира, UUID и квитанций. Это улучшает объяснение, но не закрывает требование полного live-preflight до подтверждения.

## Открытые условия выпуска

Ресурсные графы между контейнерами/игроками/модами; структурные участники всех поддерживаемых сущностей; полная матрица Create/AE2/серверной сборки; окончательная оптимизация ClickHouse/UUID-проверки большого мира; проверка актуального мира до подтверждения; профиль сети/TPS/FPS/RAM полного модпака и живого обфусцированного JAR с положительной авторизацией AvilixAuthCore. Проверка потери питания накопителя не заменяется Runtime.halt.
