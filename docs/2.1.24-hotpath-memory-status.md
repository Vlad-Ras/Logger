# AvilixLogger 2.1.24: подшипники, AE2/Create и продолжение плана памяти 2.1.23

Дата: 23 октября 2026. База: `76063c6`, ветка `feat/2.1.24-live-gui-capture-switches-20261023`.
Рабочая ветка: `fix/2.1.24-bearing-memory-20261023`.

**Статус: локально подготовленный патч; выпуск и игровая приёмка не выполнены. Новый JAR не собран.**

## Что установлено по исходникам

1. `NbtSerde.snapshotEntity()` сначала вызывает `saveWithoutId`, затем для сущности Create безусловно повторяет сохранение конструкции и дополнительное сохранение сущности. На обычном полном сохранении это лишние обходы всей структуры. Патч использует первый payload с Type и Blocks; восстановительные пути сохраняются для неполного результата. Один глубокий copy остаётся необходимым: журнал не должен держать изменяемые NBT-объекты Create.
2. `StorageHelperMixin` открывал контекст AE2 и для SIMULATE, а закрывал только через RETURN. Исключение до RETURN могло оставить подавление сетевого журнала до истечения таймаута. Теперь SIMULATE проходит без контекста, MODULATE закрывает его в finally. Таймаут контекста больше не нужен: длительная реальная операция не потеряет границу подавления своего внутреннего сетевого вызова. Пустой holder переиспользуется: в нём только depth, без Player/Level/ItemStack. Реальные ненулевые переносы сохраняются; независимые вложенные powered-операции не удаляются.
3. В `CartAutomationAudit.Scope.finish` даже пустой обычный тик Create повторно проверял авторизацию. Теперь пустой scope только освобождает состояние. Дополнительно tick-only bookkeeping использует существующий короткий lease AuthCore; публикация событий сохраняет прямую проверку авторизации.
4. В переиспользуемом scope оставалась ёмкость списков/IdentityHashMap после крупных операций. Патч заменяет разросшиеся буферы после более 64 элементов и сбрасывает `mountedCreative`, включая аварийное завершение. Очистка остаётся в finally; на пустом тике новые коллекции не создаются.
5. GUI-переключатель подшипников ранее не участвовал в ранней проверке общего BE ticker: там проверялся только конфиг. Теперь отключение через GUI также ставит контекст подавления до общих снимков событий.
6. CPU/event/journal очереди используют ограниченный handoff с ожиданием при переполнении. Следовательно, «в фоне» не гарантирует отсутствие задержки server thread. Сохраняются действующие ограничения памяти, порядок, обязательные payload отката и запрет потери событий при насыщении. Неограниченная очередь, синхронный fallback и отбрасывание строк не добавлены.

Это статически установленные лишние затраты и ошибки очистки. Их доля в наблюдаемом падении TPS пока не измерена на пользовательском сервере.

## Замер частоты и задержек

На авторизованном сервере с новой собранной версией, от OP 2+ с административным доступом:

```text
/log perf start
/log perf
/log perf stop
```

`start` начинает новую ограниченную сессию; `/log perf` показывает текущий отчёт. `stop` фиксирует отчёт и пишет его в серверный лог. Счётчики выключены по умолчанию, не сохраняют Minecraft-объекты и сбрасываются при завершении сервера.

Отчёт содержит количество и среднюю частоту принятых событий AE2, подшипников, вагонеток, прочих Create и остальных источников; количество по ActionType; длительность вызовов снятия NBT, в том числе на server thread; количество ожиданий заполненных очередей и суммарное время ожидания, отдельно для server thread. Generic `mod:create` попадает в прочие Create, когда конкретный вид ещё не известен в момент enqueue.

Это **не** счётчик подтверждённых INSERT в ClickHouse, не MSPT и не retained heap. Время NBT включает вложенные вызовы, поэтому его нельзя суммировать как exclusive self-time. Операции, начавшиеся до/завершившиеся после окна замера, могут не входить в него полностью. Ожидание самого lock и незавершённые на момент stop ожидания отдельно не измеряются.

## Выполненная локальная проверка

- Java 17 скомпилировала реальные production-классы `ActionType`, `HotPathMetrics`, `WeightedQueue` и независимый `HotPathQueueStandaloneTest`, без Minecraft-заглушек.
- `HOTPATH_QUEUE_STANDALONE_OK`: лимит байтов, порядок, удержание in-flight reservation до завершения, измерение блокировки именно world thread, остановка счётчиков, одиночный большой payload и shutdown.
- Парсинг изменённых Java-файлов проверяет только синтаксис, не типы и не Mixin-трансформации.
- `git diff --check` и синтаксис изменённых YAML проходят.

Полная сборка здесь требует Java 21 и зависимостей NeoForge. Доступна Java 17; попытка получить Java 21 с официального сервера вернула страницу недоступности. Публикацию ветки отклонила автоматическая проверка разрешений; CI для этого локального патча не запускался.

## Порядок оставшейся приёмки

1. Сборка и все регрессии Java 21; проверка защищённого candidate JAR. Сначала проверить `CREATE_BEARING_SINGLE_SERIALIZATION_OK`, отсутствие MixinApplyError и OP-only access test.
2. Копии одного мира и одинаковый актуальный модпак. Сохранить SHA-256 клиента/сервера через `tools/acceptance/inventory-modpack.py`. Старый JAR и новый кандидат тестируются отдельно с одинаковыми настройками логирования.
3. После одинакового прогрева: простой подшипников, затем активные буры/активаторы/переносы грузов, затем AE2 с реальными переносами и большим числом SIMULATE-проверок. Для каждого режима 5 минут, минимум три повторения. На кандидате включить `/log perf start`, после сценария `/log perf stop`; снять JFR и Spark MSPT/self-time.
4. Повторить поиск/пагинацию/открытие-закрытие GUI, загрузку-выгрузку чанков и смену мира клиента. Сравнить FPS/frametime и heap после GC; подтвердить очистку старых миров. Отдельно посмотреть dominators на `CreateDeployerTransaction.RETAINED`: это намеренное ограниченное удержание до 256 нативных сущностей для строгого отката AI, а не подтверждённо устранённая утечка.
5. Изолированно замедлить/отключить ClickHouse: проверить ограничение очередей, ожидания, восстановление связи, drain и отсутствие пропусков/дублирования обязательных строк. Нулевую блокировку world thread при бесконечно недоступном хранилище, ограниченной памяти и запрете потери строк этот контракт не обещает.
6. Прогнать production AuthCore и OP/обычного игрока, затем откат/конфликт/отмену/рестарт. Только после этого принять релиз. Не нужны приватные ключи в чате или публичном репозитории.
