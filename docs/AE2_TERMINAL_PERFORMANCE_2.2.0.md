# AE2: цена захвата терминала и повторные снимки

30.10.2026. Приоритет — жалоба на TPS игрока в терминале AE2. База `ed0b1d80290d51d362086d44f7fc58b69bfda2de`; ветка `work/2.2.0-ae2-terminal-cost-20261030`. Проверенный код `e16afb6ce0c604a2c146a334b59097cce49b981e`, tree `57c1be4610f8c7912f427e2bcfcc195721953912`. Выпускной JAR не создаётся.

## Конкретное изменение

Раньше общий AEBaseMenu capture копировал все поддержанные физические ItemStack до действия, затем снова копировал их после действия, даже если слот не изменился. Новый followUpSnapshot читает тот же native слот, проверяет semantic и ItemStack.matches с отделённым before. Для неизменившегося слота переиспользуется уже отделённый SlotValue; для изменившегося создаётся новая копия. Нативный ItemStack не удерживается. Compare использует этот follow-up и пропускает повторное сравнение, когда SlotValue совпадает по identity.

Передний снимок остаётся полным. Все выбранные физические слоты по-прежнему проверяются после операции; игрок/виртуальная ME сетка не добавляются к physical inventory. Отсутствующий слот или изменившийся semantic не выдаётся за опустошение контейнера. Изменение компонентов, количества и типа предмета сохраняет прежние full before/after и тип события. Settings по-прежнему экспортируются и сравниваются; не отбрасываются ни изменения настроек, ни неизвестные клиентские действия. Ошибка чтения возвращает null, а не пустую сторону.

Before/follow-up принадлежат одному синхронному capture и считаются read-only: общий detached SlotValue нельзя изменять между ними. Production before хранится в приватном поле scope и не модифицируется; native изменения после снимка не меняют эти данные. Нового постоянного кеша, удержания меню/мира в worker, tick handler, обхода grid или capability lookup нет. Compare больше не заходит во второй enabled check через capture: его собственная прямая проверка AuthCore/category/logAe2 и server-thread guard остаются перед follow-up. Авторизация не кешируется новым путём; отключение capture между сторонами прекращает compare до follow-up.

Дополнительно NetworkStorage insert/extract callbacks теперь отсекают SIMULATE и null key/source до powered-scope lookup; MODULATE с actual<=0 также выходит до ThreadLocal и transfer dispatch. Результат native операции не меняется, исходный requested amount не подменяет actual, положительный MODULATE сохраняет прежний powered dedup и authorization/publication путь. Callback инъекция и сами проверки всё ещё имеют стоимость; это не обещание нулевых затрат симуляции. Существующие native transfer проверки simulation/zero, full key/long и powered nesting сохраняются; отдельного численного IO-hook выигрыша этот стенд не измеряет.

## Что измеряет новый стенд

В запитанную dev grid добавлена настоящая обычная ItemTerminalPart и MEStorageMenu. Дополнительный terminal node подключён известной dev связью, остаётся в том же forced chunk и удаляется штатной cleanup стенда. Состав пользовательского модпака и production chunk tickets не меняются.

Dev subclass MEStorageMenu переопределяет только входы Ae2MenuCapture счётчиками; они никогда не разрешают capture или append. Настоящий native receiveClientAction с no-op сначала должен дать один before/after вызов, доказывая работоспособность probe. Затем 1 000 прямых native broadcastChanges без действий должны дать ноль входов Logger action capture. Это проверка маршрута вызовов на настоящем терминале, с dev probe и выключенной авторизацией. Это не 1 000 естественных server ticks, не измерение idle MSPT, не положительный authorized production trace и не доказательство отсутствия любой работы остальных подсистем Logger.

Для snapshot kernel все пять настоящих view-cell slots заполняются VIEW_CELL с CustomData 4 KiB. Read-only before снимается один раз. Follow-up должен переиспользовать все неизменившиеся SlotValue и не создать строк. После component-only изменения одной ячейки должен появиться ровно один новый SlotValue и одна запись, идентичная full-copy reference по типу, source/actor/address и обеим полным NBT сторонам. После удаления live предмета отделённый after сохраняет свои компоненты. Отдельный worker не имеет права читать follow-up native state.

На серверном потоке используется JDK ThreadMXBean: 50 000 warm-up пар, затем пять раундов по 20 000 вызовов A1=полный повторный snapshot + поиск изменений, B=follow-up по before + тот же поиск изменений, A2=полный повторный snapshot + поиск изменений. Для каждого вызова проверяется пустой no-op результат. Это одинаковая post-action работа: сравнение предметов входит в обе стороны, хотя новый путь выполняет его раньше. Volatile dev sink делает результат escaping. По каждому из трёх показателей публикуется отдельная медиана пяти раундов. Измеряются выделенные байты, CPU nanos и wall nanos; idle обновления, первый before, native action, кодирование непустых rows/NBT/storage и warm-up в эти три выборки не входят. Обязательная проверка — B выделяет меньше байтов, чем оба A; временные величины публикуются без нестабильного CI порога.

Это сравнение второго snapshot вместе с no-op diff, а не всей операции: первый полный before, нативное действие AE2, формирование непустых строк и очередь по-прежнему имеют цену. Маленькая dev grid и пять физических ячеек не представляют большой production ME каталог, терминал крафта или remote providers. Числа CPU/wall не переводятся в выигрыш TPS/MSPT.

## Результаты

[Четыре серверных профиля и настоящая ClickHouse](https://github.com/Vlad-Ras/Logger/actions/runs/40966152319), [GUI](https://github.com/Vlad-Ras/Logger/actions/runs/40966152149) полностью успешны на указанном source commit. AE2_TERMINAL_COST_NATIVE_OK обязателен перед AE2_NATIVE_OK и получен на 19.2.12/19.2.18. В обеих версиях: idleBroadcasts=1000/auditEntries=0, positive live-action probe=1, unchangedReused=5, changedCopies=1; 50 000 warm-up пар, 5 A/B/A раундов по 20 000 вызовов на выборку, отдельные медианы показателей.

| AE2 | Байт/вызов A1 / B / A2 | CPU нс/вызов A1 / B / A2 | Wall нс/вызов A1 / B / A2 |
| --- | --- | --- | --- |
| 19.2.12 | 2096 / 1696 / 2096 | 701 / 625 / 649 | 701 / 665 / 649 |
| 19.2.18 | 2064 / 1664 / 2064 | 643 / 613 / 648 | 643 / 614 / 648 |

В этом post-snapshot+no-op diff ядре B выделяет на 400 байт меньше за вызов: −19,1% для 12 и −19,4% для 18. Медианное CPU B ниже обоих контролей: 625 нс против 649–701 нс и 613 нс против 643–648 нс. Wall 12 B находится между контролями; универсальный wall speedup не заявляется. Это gross thread allocation, не retained heap. Результаты двух версий получены на разных CI runners и не доказывают преимущество одной версии AE2 над другой. Нельзя переносить эти проценты на всю операцию Logger, серверный TPS/MSPT или пользовательский каталог.

Пройдены compileJava/compileCreateSmokeJava/testAsyncPipeline/testCreatePreflight/verifyMixinSafety, Java 21 ProfileSummaryTest, Python inventory/profile comparison, AE2 absence, Create, Create absence, Backpacked и actor/aircraft regressions. Сохранены 52 device rows/56 pattern rows, remote 11/13, grid 6 saturation cases/9 rows, crafting 14, assembly 7/3 jobs/2 finish, processing 3/2 finish, 10 autonomous cancellation jobs/9 neutral + 1 UI, native disk lifecycle через 3 server processes с nativePause=false/true для 12/18. ClickHouse повторно проверила exact full key/long/actor/address/ID/details в minimal mode после нового подключения; CART_GUI_CLIENT_OK сохранил отрисовку на 320×240, 640×360 и 960×540. Это не positive AuthCore end-to-end. Ранний snapshot-only стенд c9a5545 прошёл функциональные проверки; a848c4f добавил одинаковый diff к обеим сторонам. Его одиночные CPU выборки A1/B/A2 дали 7 418/6 926/3 834 нс на 19.2.12 и 6 895/4 631/2 914 нс на 19.2.18: сильный разогрев между контролями не позволяет объявить ускорение CPU. Поэтому 40d20e8 увеличивает warm-up и использует пять A/B/A раундов с медианами; snapshot production код между этими ревизиями не менялся. e16afb6 затем добавляет описанный ранний фильтр network callbacks; итоговый CI относится к нему. Предварительные времена не используются как итоговый выигрыш.

Native device/settings (52 rows) и pattern/provider/press (56 rows) теперь используют новый after kernel в существующих проверках полных данных. Сохраняются остальные menu/remote/grid/transfer/crafting/assembly/processing/link cancellation и disk lifecycle регрессии. Локально прошли git diff --check и Python inventory/profile tools; полная локальная Java 21/Gradle/native компиляция не засчитывается.

## Жалоба на 1.2.22 и остающаяся приёмка

Проверена именно ветка build/1.2.22-unified-gui, commit `f1aaea0a5951703f8d99d5214b54dd360cd4405d`, а не предположительно исправленный номер. Её прямые AE2 menu hooks также окружают действия, без snapshot на broadcast/tick. При действиях есть synchronous slot/settings copies и item NBT capture, а queue.put может ждать свободного места. Отсутствие прямого idle hook не исключает косвенную работу других интеграций, AE2 native обновления или давление storage. Соответствие установленного JAR этой ветке и причина конкретной просадки без server Spark/JFR не установлены; эта версия не исправляется/не пересобирается данным пакетом.

В текущей 2.2.0 сохраняются native live key/item encoding на сервере, bounded byte accounting/backpressure и прежний worker для SNBT/JSON/journal/БД. Истинное заполнение очереди этим не устраняется. Сопоставимый server A/B/A профиль closed/idle/actions на пользовательском каталоге, positive AuthCore → hook → storage → GUI, весь transformed модпак/configs/scripts и ферма 8 пил + 8 активаторов с саженцами + portable storage interface остаются открытыми. Scguns 1.5 manual stop, численные heap/GC/MSPT/latency и остальные модовые контракты не закрываются; поезда и удалённый портал не возвращаются.
