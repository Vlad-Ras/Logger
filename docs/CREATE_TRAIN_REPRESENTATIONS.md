# Представления поездов: начало следующего направления

После контракта внешних данных активатора начата подготовка возврата выгруженных и портальных представлений вагонов Create 6.0.11.

## Что добавлено

Lifecycle-снимок адресуемого активного вагона содержит `TrainRepresentations`: ID состава, постоянный ID и индекс вагона, нативный payload Carriage, палитру измерений и версию общего груза. Нативный payload сохраняет serializedEntity, пассажиров, bogey/travelling points и EntityPositioning для всех представлений, включая отсутствующую живую сущность. Сохранение выполняется на границе события; периодического сканирования поездов нет. Временная сериализация не расходует ForceYaw живых представлений.

`CreateTrainRepresentationState.prepare` отделяет данные от истории, проверяет ID, типы списков, адреса измерений, уникальность представлений и пределы (до 16 измерений, до 128 MiB). Он не создаёт сущность, не загружает чанк и не меняет RailwayManager. Непривязанное представление и состояние после окончательной разборки получают `TrainRepresentationsComplete=false` с причиной; они не выдаются за полный активный payload. Прежние lifecycle-события и откат обычной разборки сохраняются.

## Проверки и следующий шаг

Поездной native fixture проверяет payload двух измерений, одно отсутствующее представление, выгруженную сущность, сохранность Train/Carriage ID, независимость подготовленного снимка и отказ при потере EntityPositioning. Прежние 23 сценария разборки, компенсации, конфликтов, очередей, станции, сигналов и груза остаются в регрессии.

Полный откат портального перехода пока не включён. Следующий шаг — зарезервированный Job для набора представлений с общей Carriage.storage, проверки актуального RailwayManager/графа/состава, поэтапное создание и привязка нужных сущностей, компенсация после частичного появления и защита от дублирования груза/UUID. Только после этого можно разрешать соответствующий пользовательский откат; сохранение нового payload само по себе не является таким разрешением.
