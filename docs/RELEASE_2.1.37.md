# AvilixLogger 2.1.37

Minecraft 1.21.1, Java 21, **NeoForge 21.1.259**. Отдельная ветка: `work/2.1.37-client-reports`. Файл: `avilixlogger-2.1.37.jar`.

## Изменения относительно 2.1.36

1. Клиент отвечает через соединение конкретного запроса, даже до появления `Minecraft.player`. Прежняя проверка глобального `Minecraft.getConnection()` могла молча отбросить запрос при входе.
2. Список модов/версий/названий и выбранных ресурс-паков передаётся до открытия модовых архивов для SHA-256. Долгий/занятый хэширующий worker больше не задерживает первичный отчёт.
3. SHA-256 модов и паков дополняют тот же отчёт отдельными пакетами до 30 KiB. Части привязаны к запросу и соединению; чужие/повторные/переставленные части отвергаются.
4. При добавлении хэшей сохраняется полный состав уже полученного списка, в пределах существующих лимитов 512 модов / 128 паков. Новый согласованный канал v5 обслуживает увеличенный ответ администратору; старый v4 получает прежнее ограничение с признаком сокращения.
5. Чтение из ClickHouse сохраняет полный дополненный отчёт вместо повторного применения лимита serverbound-пакета. Формат таблицы и JSON сохранён.
6. Чтение сохранённых отчётов и запись новых разведены по отдельным ограниченным пулам. Медленное чтение больше не занимает единственный поток записи.
7. Полученные данные показываются до подтверждения ClickHouse; GUI явно различает получение, подсчёт хэшей, сохранение и ошибку сохранения. Суточный интервал по-прежнему отмечается только после подтверждённой записи.
8. Повторный запрос от того же администратора перепривязывает ответ к последнему ID GUI. Раньше итог мог уйти на старый ID и быть проигнорирован экраном.
9. Проверка автоматического запроса после входа обрабатывает до восьми клиентов в секунду, а не одного; при прогреве хранилища автоматически не запускается повторное чтение клиентских архивов.
10. В GUI три отдельные кнопки существующих типов LoggerGuiWidgets: «Запрос отчёта», «Открыть сохранённый», «Обновить (онлайн)». Поле ника вынесено в отдельную строку; вкладки/поиск/прокрутка сдвинуты согласованно.
11. Добавлены регрессии раннего запроса до появления игрока, блокировки SHA-256, повторного запроса GUI, разрыва соединения, границ пакетов, полного состава большого отчёта, хранения и разделения I/O.

## Три действия

| Кнопка | Поведение |
| --- | --- |
| Запрос отчёта | Создать первый отчёт у игрока онлайн или открыть уже подтверждённый отчёт за текущий суточный интервал. Для офлайн-игрока открыть сохранённый. |
| Открыть сохранённый | Только прочитать последний отчёт за 24 часа; не запрашивать клиент. |
| Обновить (онлайн) | Запросить новый сбор независимо от суточного интервала, если игрок сейчас в сети. Активный сбор переиспользуется с новым ID ответа GUI. |

Быстрый сбор требует обновления сервера **и клиентов проверяемых игроков**. Старый клиент продолжает отвечать прежним способом, с ожиданием SHA-256; обновлённый клиент со старым сервером также использует совместимый прежний ответ. Установка только на админклиент не обновляет сбор на других клиентах.

## Возможности ветки

Сохранены логирование, поиск/GUI, обычный откат и восстановление после краша с WAL, проверка предметов/поддержанных жидкостей, выгрузка серверных логов и открытие клиентской папки, обфускация и штатный AuthCore. Подробный перечень унаследованных функций: [2.1.35](CANDIDATE_2.1.35.md), [2.1.36](RELEASE_2.1.36.md). Оставшиеся ограничения модпака, восстановления и положительной штатной авторизации не объявлены закрытыми.

## Проверки

Итоговые проверки: `testAsyncPipeline`, `testCreatePreflight`, `verifyMixinSafety`, `verifyObfuscatedJar`, полный native Create-прогон и настоящий клиентский GUI на NeoForge 21.1.259 — успешно.

- `CLIENT_REPORT_FAST_PATH_OK`: первый отчёт приходит до завершения заблокированного хэширующего future и при отказе его worker; проверен fallback для старого сервера.
- `CLIENT_REPORT_EARLY_CONNECTION_OK`: реальный клиентский hook вызван при `Minecraft.player == null`, с двумя соединениями и заблокированным future хэшей. Первичные отчёты получены сразу; после отключения первого соединения поздние хэши уходят только второму. Payload перехватывается стендовым контекстом соединения; это не производственный вход с положительным AuthCore.
- `CLIENT_REPORT_REPLY_REPLACEMENT_OK`: production-обработчик активного запроса перепривязал ответ к новому ID GUI того же администратора.
- `CLIENT_REPORT_IO_ISOLATION_OK`: два заблокированных чтения не задерживают отдельную запись.
- `CLIENT_REPORT_HASH_WIRE_OK`: 512 модов / 128 паков; две части хэшей, максимум 28 358 байт, всего 36 799 байт; полный согласованный ответ v5 — 39 017 байт. Serverbound-лимит 30 KiB не повышался.
- `CLIENT_REPORT_HASH_STORAGE_CODEC_OK`: JSON 81 149 байт сохраняет все моды, паки и хэши при чтении из хранилища.
- Проверены суточное ограничение только после ACK, старые форматы, непротекание содержимого отчёта в консоль и игнорирование старого ID GUI.
- GUI: три кнопки проверены и визуально осмотрены; используются существующие ScaledTextButton/ScaledEditBox. Полный клиентский прогон проверил размеры 320×240, 640×360, 960×540, передачу diagnostics.log и открытие папки.

## Дополнительное исправление чтения JarJar / UnionFileSystem

Клиентский стек 2.1.36 подтвердил `UnsupportedOperationException` в `UnionFileSystemProvider.newByteChannel`, вызываемом через `JarJarFileSystems 0.4.1` при подсчёте SHA-256. В SecureJarHandler 3.0.8 этот канал допускает только пустой набор опций либо READ. Прежнее открытие с `NOFOLLOW_LINKS` вызывало отказ; исключение обрывало весь collector. Номер выпуска остался 2.1.37, выданный файл заменён исправленной сборкой.

- Локальные файлы продолжают открываться с NOFOLLOW_LINKS. Loader-owned виртуальные пути читаются стандартным потоком, поддерживаемым ZIP/JAR/JarJar/Union.
- Отказ провайдера/доступа у одного файла даёт недоступный SHA-256 этого файла и не отменяет сбор остальных сведений.
- Добавлены проверки точного SHA-256 обычного и вложенного JAR, закрытого провайдера, локальной символической ссылки и недопустимого пути пакета.
- Холодный запуск реального ModList на клиентском стенде: провайдеры `file=8`, `jij=2`; получены 10 модов и 9 хэшей. Все доступные для чтения модовые файлы, включая виртуальные, имеют хэши. Нехэшируемый путь каталога не выдаётся за архив.
- Дополнительно проверен реальный обфусцированный JAR: точный SHA-256 файла внутри ZIP/JAR совпал с независимым MessageDigest.
- `testAsyncPipeline`, `verifyMixinSafety`, `verifyObfuscatedJar` и клиентский прогон с реальным хэшированием прошли.
- Повторный клиентский профиль: 967 кадров, 59.0 FPS, p95 18.88 ms, p99 30.10 ms, наблюдаемый heap всей JVM 543.0 MiB. Три кнопки, GUI, передача логов и открытие папки остаются проверенными. Серверная логика не менялась; результаты полного серверного прогона 2.1.37 выше относятся к той же серверной реализации.

Для устранения этой ошибки нужен исправленный JAR на клиенте, на котором возникает исключение. Совместимость с сервером 2.1.36 сохраняется через прежний протокол; быстрая поэтапная доставка и полная новая логика отчётов требуют также сервера 2.1.37. NeoForge остаётся 21.1.259.
