# Нагрузка и скорость AvilixLogger 2.2.0

Направление добавлено пользователем 25.10.2026 отдельно от оптимизации ОЗУ. Направление совместимости серверного модпака продолжается; работа над поездами остановлена по указанию пользователя. Портальный переход вырезан из игровой сборки и не является задачей выпуска.

## Обязательное поведение

- Logger должен минимизировать собственную работу в серверном потоке и работу других модов, которую вызывают его перехваты, снимки и запросы capability. Низкий размер heap не считается доказательством низкой нагрузки.
- Чтение живого мира, сущностей, инвентарей, capability и нативный сериализатор мода выполняются в серверном потоке. Перенос этих вызовов на CPU-worker создаёт гонки; отделённые данные обрабатываются в фоне.
- SNBT/JSON-кодирование, сравнение снимков, форматирование, построение планов, поиск, сортировка, файловые операции, сетевые запросы и БД выполняются вне серверного потока, когда входные данные уже отделены. Фоновое задание не должно удерживать Player, Level, Menu или mutable ItemStack вместо снимка.
- Нет дополнительного ticking модов, сброса/переэкипировки их содержимого, отправки игровых действий или принудительной загрузки чанков ради наблюдения. Подписки на штатные события предпочтительнее опроса.
- Проверка отключённой категории происходит до снимков и обходов содержимого. Повторный модовый сериализатор после его ошибки не вызывается; неполный снимок не заменяется фиктивным полным NBT.
- Применение и компенсация откатов бюджетируются по тикам. Их фактическая цена, включая дорогостоящий единичный вызов мода, проверяется отдельно.
- Не снижать нагрузку скрытым удалением событий, ресурсных дельт, обязательных снимков или проверок AuthCore/OP.

## Сделано в этом проходе

1. Один вызов `BlockEntity.saveWithFullMetadata` вместо цепочки повторных reflective save после ошибки. Возвращается отделённая копия либо явное отсутствие снимка. Счётчик ошибок ограничен.
2. Проверка server thread и уже загруженного чанка до чтения блока/capability. Закрытие удалённого меню не загружает чанк ради журнала. Сериализатор сущности также не запускается в фоне.
3. Обход кликов при отключённой категории контейнеров начинается до чтения игрока/меню; пакет с чужим containerId не запускает захват.
4. Счётчики диагностики не удерживают неограниченное число UUID конструкций/координат механизмов. Переполнение сводится в счётчик `[other]`; сам журнал не теряет строки.
5. Задание разниц контейнера не захватывает `MenuAction` и через него Player/Level/Menu. Проверка байткода синтетического lambda-метода входит в regression.
6. Анализатор JFR schema 2 различает `server_execution_samples_logger_self`, `logger_called`, `wrapped_simulation`, `unattributed`. Вызванный Logger сериализатор относится к `logger_called`; обычный тик мода ниже `avilixlogger$withSource` — к `wrapped_simulation`. Это классификация сэмплов по стеку, не точное измерение времени каждого вызова.

## Что ещё требуется измерить

- Сравнение без Logger / исходный Logger / кандидат: одинаковый мир, моды, Java, конфигурации, число игроков и нагрузка; одинаковый прогрев, минимум три повторения.
- Idle; обычные контейнеры; большие модовые инвентари; ферма на подшипнике с 8 пилами, 8 активаторами/саженцами и portable storage interface; массовые изменения блоков; поиск/откат большой истории; медленная и недоступная БД.
- MSPT p50/p95/p99 и максимумы, allocations/s, heap после GC, паузы GC, очередь/ожидание на server thread, скорость записи, время до видимости строки, задержка поиска и начала/завершения отката.
- Отдельно цена вызовов других модов из NbtSerde/ContainerSlotSnapshot и других захватов Logger. Простого процента стека с обёрткой Logger недостаточно.
- Отдельный клиентский профиль памяти/времени кадра, поскольку оптимизация сервера не подтверждает FPS клиента.

## Существующее ограничение насыщения

`WeightedQueue.put` использует блокирующее противодавление. При переполнении CPU/event/journal очереди producer, включая серверный поток, может ждать. Вынесение обработки в фон само по себе не решает это ограничение. Безграничная очередь, синхронное кодирование на сервере или незаметная потеря событий не добавляются. Дальнейший способ обработки длительной перегрузки должен проверяться вместе с ограничениями памяти и сохранностью журнала; гарантировать отсутствие задержек при произвольно долгом отказе БД сейчас нельзя.

Реальные авторизованные замеры полного модпака ещё не получены. Нельзя объявлять исчезновение прежних ~60 000 мкс/тик в Observable по одному CI smoke.
