# Приёмка 2.2.0 на полном модпаке

Эти инструменты собирают доказательства на настоящей JVM. Они не заменяют профиль готовыми числами и не снимают проверку AuthCore. Снимки миров и исходные записи профиля остаются у оператора; не публикуйте ключи AuthCore, конфиги с паролями или полные серверные логи в публичном репозитории.

## Совпадение среды

Для сервера и клиента отдельно сохраните список точных JAR:

```sh
python3 tools/acceptance/inventory-modpack.py /path/to/mods /path/to/results/server-mods.json
```

Исторический `latest.log`, добавленный пользователем 05.10.2026, содержит Logger 2.1.8, Create 6.0.10, AE2 19.2.18, Framework 0.13.11, Backpacked 3.0.5 и FD 1.3.2. Основной стенд разработки использует Create 6.0.11-313, AE2 19.2.12 и Framework 0.13.10. Дополнительная матрица CI `logged-pack` компилирует и прогоняет Create 6.0.10-281 / AE2 19.2.18 / Framework 0.13.11 / FD 1.3.2, включая Backpacked. Это проверка совместимости указанных версий; Maven-артефакт без исходного SHA-256 не объявляется точной копией JAR из лога. Этот лог не подтверждает актуальность набора и не содержит сравнения heap. Для приёмки нужен текущий набор JAR с SHA-256; имя версии само по себе не идентифицирует байты мода.

Сравните исходный Logger и кандидат в копии одного мира, на одинаковых Java 21, аргументах heap, конфигурациях и оборудовании. После одинакового прогрева повторите одну нагрузку минимум три раза. Не сравнивайте простаивающий клиент с сервером под нагрузкой. Зафиксируйте число игроков, дистанции прорисовки, загруженные чанки, активные конструкции и длину очередей Logger.

## JFR

После прогрева найдите нужную JVM через `jcmd -l`. Из корня репозитория:

```sh
tools/acceptance/capture-profile.sh 12345 baseline-server /path/to/results 120
```

Команда запускает ограниченную по времени запись и завершает свою работу сразу. После окончания записи:

```sh
java tools/acceptance/ProfileSummary.java /path/to/results/baseline-server.jfr > /path/to/results/baseline-server-summary.json
```

Повторите на кандидате с тем же сценарием:

```sh
python3 tools/acceptance/compare-profiles.py /path/to/results/baseline-server-summary.json /path/to/results/candidate-server-summary.json > /path/to/results/server-comparison.json
```

Повторите отдельно для клиента. Запись `settings=profile` имеет собственную нагрузку; настройки и длительности должны совпадать. Если запись создаётся встроенным `/jfr start` → `/jfr stop`, анализатор также читает её непосредственно. Наличие `minecraft.ServerTickTime` зависит от способа включения Minecraft-профилирования; отсутствие поля MSPT обозначается `null`. Для MSPT p95/p99 нужен отдельный Spark-профиль или исходный ряд длительностей тиков, для FPS и времени кадра — клиентские замеры. Максимум среднего MSPT из JFR нельзя называть p99 тика.

Анализатор читает события последовательно. Сумма весов allocation samples — статистическая оценка аллокаций; стек с `com.roften.avilixlogger` показывает связь с вызовом Logger, но не точный удерживаемый heap мода. `last_heap_after_gc_bytes` и `max_heap_after_gc_bytes` относятся ко всей JVM. Сравнение возвращает `null`, когда данных нет, и не выставляет автоматический PASS по отсутствующим метрикам.

## Сценарии и критерии

- Сервер: простой после прогрева; обычные блоки/контейнеры/BE; активная цепочка Create со снимка пользователя; поезд с выгрузкой; Backpacked; очередь при задержанном ClickHouse; поиск и отмена предпросмотра; остановка и повторный запуск. Сравнивайте размер мира и полноту журнала, чтобы экономия памяти не была следствием потери событий.
- Клиент: мир с одинаковой камерой; журнал с большой историей; все категории действий; прокрутка/поиск/подтверждение/отмена; справка; несколько GUI scale; разрешённый и запрещённый пользователь. Сохраните FPS, время кадра, heap после GC и скриншоты требуемых экранов.
- Производственный путь: настоящий AvilixAuthCore разрешает только подходящий сервер; без разрешения запись и действия остаются закрыты. Настоящий ClickHouse сохраняет связанные строки, поиск видит их после подтверждённого flush, перезапуск сохраняет историю. Проверить модовый редактор табличек через реальный клиент и сервер.
- Откаты: содержимое и компоненты предметов/жидкостей совпадают с ожидаемыми; повторное подтверждение не дублирует ресурсы; конфликт/отмена/выход игрока/остановка после частичного появления компенсируются. Для восстановления представлений существующий поезд, позиции и общий груз сохраняются. Портальные переходы исключены пользователем из игрового набора и из приёмки.

До получения этих файлов измерения полного модпака и production-приёмка остаются открытыми. Секретный ключ AuthCore передавать не требуется: проверка выполняется на авторизованном стенде оператора.

## Цена Logger и цена штатных тиков модов

Новый анализатор schema 2 отдельно считает серверные execution samples `logger_self`, `logger_called`, `wrapped_simulation`, `unattributed`. Наличие обёртки Logger в стеке не означает, что нативный тик под ней вызван логированием. Вызов сериализатора мода из NbtSerde, напротив, относится к работе, инициированной Logger. Показатели являются сэмплами; их нельзя выдавать за точное время вызова или суммарный CPU всех потоков. Старые `logger_stack_*` сохранены для совместимости, но не являются доказательством собственной нагрузки. MSPT и end-to-end latency измеряются отдельно.

`compare-profiles.py` принимает schema 1 и 2. При сравнении разных схем старые `logger_stack_*` не сопоставляются: правила атрибуции изменились. При двух schema 2 добавляются отдельные частоты серверных ownership-сэмплов. Тесты включают чтение настоящей временной JFR-записи и обработку отсутствующих Minecraft-метрик.
