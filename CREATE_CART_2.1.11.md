# AvilixLogger 2.1.11 — вагонеточные конструкции Create

Интеграция рассчитана на NeoForge 1.21.1 / Create 6.0.11. Create остаётся необязательной зависимостью. Авторизация AvilixAuthCore, AE2, прежние команды и обфускация сохранены.

## Учёт и поиск

Каждая MountedContraption получает постоянный UUID `AvilixCartAudit.Id`. Он сохраняется при сборке, выгрузке/загрузке, упаковке ключом Create, перемещении предмета и повторной установке. Это UUID истории, а не временный UUID сущности Minecraft.

Автор берётся из действия игрока, последнего точного действия на позиции сборщика, сохранённого владельца вагонетки или игрока, поставившего сборщик. Случайный ближайший игрок владельцем не назначается. У ранее существовавшей конструкции без таких данных владелец может остаться неизвестным.

Записываются сборка, разборка, упаковка, установка, загрузка, выгрузка, удаление, взаимодействия, изменение структуры, изменения зарегистрированных штатных mounted storage и базовой вагонетки, изменение статуса и работа с блоками мира. Движение записывается при переходе чанка и каждые 100 тиков в движении; полный NBT каждый тик не снимается. Окончательные NBT и инвентарь разобранных блоков захватываются после unmount Create.

| Команда | Действие |
| --- | --- |
| `/log cart find <игрок>` | Конструкции по последним 200 действиям игрока |
| `/log cart held` | История конструкции в основной руке |
| `/log cart history <UUID> [before]` | 25 записей с продолжением по ID |
| `/log cart rollback <UUID> <ID записи>` | Предпросмотр отката к контрольной точке |
| `/log cart confirm` | Подтверждение в течение двух минут |
| `/log cart cancel` | Отмена с возвратом применённых блоков |

Нужны обычные права lookup/rollback уровня 2. Контрольные точки — сборка, установка, упаковка, разборка, удаление и завершённый откат. Произвольная запись движения не является полным снимком.

В GUI категория **Create: вагонетки** ищет по UUID конструкции и тексту владельца/контекста. Фильтр истории сохраняется при переходе в подробности и при копировании запроса. Для связанных автоматических передач подробности показывают машину, адрес внешнего хранилища, номер слота или бака, количество до/после, компоненты и UUID операции. Владелец конструкции и исполнитель действия — разные поля: автоматическая операция без точного контекста игрока записывается от `SYSTEM`.

## Автоматический обмен предметами и жидкостями

Версия 2.1.11 связывает изменения груза вагонетки с внешними слотами/баками в рамках одного штатного тика BlockEntity Create. Поддержаны обе стороны обмена через переносные интерфейсы Create и стандартные capability: одиночный и ванильный двойной сундук (обычный/сундук-ловушка) через `InvWrapper`, `ItemStackHandler` с унаследованными штатными методами, одиночный `FluidTank` и `SmartFluidTank` Create с унаследованными fill/drain. Для составного бака Create адрес нормализуется к его контроллеру. Это контракт обработчика, а не обещание поддержки любого блока стороннего мода.

Каждая передача получает отдельный UUID. Журнал сохраняет последовательность изменений груза и парные снимки затронутых внешних ячеек: измерение, позицию, сторону доступа, block state, тип BlockEntity, класс обработчика, размер, вместимость и предмет/жидкость со всеми компонентами. Симуляции не создают передачу; частичное принятие записывается по фактически изменившемуся содержимому. Переполнение пределов, неизвестный адрес/обработчик, ошибка операции или обмен нескольких конструкций не разрешают одиночный откат.

Построитель плана проверяет наличие всех частей операции, точный баланс каждого предмета/жидкости с компонентами и непрерывность снимков между операциями, включая границы страниц истории. Слот, доступный с нескольких сторон, считается одной физической ячейкой. Внешние слоты без итогового изменения не применяются. Обработка одной операции ограничена 512 изменениями груза, 512 внешними ячейками и 1024 адресованными обработчиками; многобаковый обработчик свыше 64 баков не захватывается и штатный адаптер отката допускает только один бак.

Перед изменением мира проверяются доступность всех внешних чанков, тот же BlockEntity, адрес, обработчик, размер/вместимость и точное содержимое каждой ячейки. Предметы и жидкости декодируются в фоне строгими native codec: неизвестный или повреждённый компонент отклоняет план. Ячейка, блок которой также изменялся в откатываемой истории, требует отдельного согласования порядка и сейчас отклоняется. Заполнение, извлечение или замена содержимого поддерживаемых обработчиков блокируются на время операции, в том числе при повторном получении нового `InvWrapper` на зарезервированном блоке.

Внешние ячейки применяются и проверяются по одной под общим бюджетом координатора. Отмена/ошибка возвращает уже изменённые внешние ячейки, слоты игроков и блоки мира из готовых снимков. При штатной остановке компенсация завершается до сохранения. Принудительной загрузки чанков и поиска неизвестного внешнего хранилища нет.

## Нагрузка

Неизменившийся тик не сканирует инвентари и соседние сущности и не сериализует NBT. Запись изменения слота выполняется по событию, симуляции insert/extract не логируются. Снимок живого мира отделяется на серверном потоке, SNBT/поиск/построение плана/глубокие копии для восстановления выполняются в фоне. При упаковке используется уже созданный Create payload. Для автоматизации переиспользуется контекст тика; копируются только ячейки вокруг реального вызова поддерживаемого API. В тик машины, которая обращается к таким обработчикам, копия до операции делается даже тогда, когда обмен в итоге не затронул вагонетку. Сканирования инвентарей в простое нет; производительность на реальном модпаке не измерялась.

Поиск предмета при откате пошагово проверяет онлайн-инвентари, ender chest, до 64 записанных позиций контейнеров и событийный индекс загруженных предметов. Глобального обхода сущностей/чанков и принудительной загрузки выгруженных чанков нет. На время операции уже загруженные нужные чанки удерживаются билетом.

Восстановление структуры, проверка и изменение мира, проверка и удаление связанного дропа выполняются по частям: максимум 16 шагов с проверкой бюджета около 1 мс между шагами. Один native codec/сохранение NBT/initialize storage не прерывается посередине и может превысить этот бюджет. Это не гарантия отсутствия задержек при любом размере или стороннем моде. Лимит плана — 100000 событий / 128 MiB.

## Безопасность отката и границы

Перед изменениями проверяются текущие block state, полный NBT и слоты, доступность целевого чанка, единственность ID и текущее представление конструкции. Сущности, блоки и поддержанные capability на время операции блокируются. Новые сущности сначала создаются и регистрируются; затем убирается исходное представление. При ошибке до фиксации или отмене применённые блоки возвращаются из временных резервных копий по тикам. Завершённый откат записывает новую контрольную точку; пересекать предыдущий откат старым планом нельзя.

Обмен предметами с игроком через штатные меню mounted storage и базовой вагонетки теперь имеет связанный снимок: UUID операции, изменённые слоты конструкции, слоты игрока и курсор. Снимки делаются только вокруг клика и закрытия меню; прямые изменения стека в `ItemHandlerContainer.removeItem` тоже учитываются. Перемещение внутри инвентаря при открытом меню и возвращение курсора в инвентарь при закрытии также связываются с историей. Общие обработчики двойных сундуков разбираются через их штатную адресацию. В фоне проверяются наличие всех частей, баланс количества/компонентов предметов и непрерывность изменений каждого слота. Слоты без итогового изменения не применяются. Старые неподтверждённые записи внешнего обмена по-прежнему не разрешают откат; обновление не восстанавливает отсутствующие снимки задним числом.

Перед изменением мира нужные получатели должны быть онлайн, а затронутые слоты должны точно совпадать с последним снимком. Нативные изменения инвентаря, клики, использование/выбрасывание предметов и тик игрока временно защищаются только для участников отката. Слоты получателей изменяются и компенсируются по одному под тем же бюджетом тика. При выходе участника его уже изменённые слоты (не более 42) возвращаются из готовых `ItemStack` до штатного сохранения игрока; мир и остальные получатели компенсируются по тикам. Разбор предметов получателей выполняется в рабочем потоке. Это резервирование не является адаптером для произвольных модов, напрямую изменяющих живые стеки или сохраняющих игрока в обход нативных API.

Дроп от работы бура и созданный клей учитываются отдельно. Оставшаяся в мире часть дропа удаляется только при точном совпадении со снимком. Проверка и удаление большого количества предметов не выполняются одним циклом в обычном тике. Обычное создание/перемещение/работа конструкции не ограничивается этими правилами.

Подбор помеченного дропа игроком теперь записывается после завершения штатного `playerTouch`: фактически принятое количество, остаток сущности и изменённые слоты получателя. Отменённый подбор и задержка не считаются принятым предметом; снимок инвентаря начинается только перед нативным `Inventory.add`. Учтён полный и частичный подбор, несколько последовательных получателей и последующее возвращение предмета через учтённое меню конструкции. При откате созданного после контрольной точки дропа полученные предметы забираются из точных слотов получателя, а оставшаяся часть удаляется из мира после фиксации. Полностью подобранная сущность должна отсутствовать; повторное появление того же UUID останавливает откат. При отмене и выходе игрока действует та же компенсация слотов.

Подбор без связанных снимков, дроп, созданный до выбранной контрольной точки, неучтённое объединение/изменение стека и последующее перемещение/использование полученных предметов требуют расширенной истории. Такие планы отклоняются, как и несовпадение оставшегося в мире количества.

Совместный откат сцепок, вложенных конструкций и произвольных изменений внешних сущностей **пока не реализован**. Автоматический обмен разрешается только для полностью связанного протокола и стандартных обработчиков, описанных выше. Отдельных адаптеров требуют произвольные составные и sided capability, обработчики с переопределёнными методами, ленты/депо, разлив жидкости в мир, преобразование в вёдра и обратно, прямое изменение Container ванильной воронкой и операции вне штатного тика BlockEntity Create. Сюда же относятся последующее перемещение/использование полученного игроком груза, преобразование предметов или выбрасывание через меню с несходящимся балансом. Такие одиночные откаты отклоняются до фиксации, чтобы не создать дюп или уничтожить изменения получателя. Контекст тика сам по себе не считается доказательством внутреннего обмена: безопасным внутренним поступлением считается захват дропа штатным block breaker; другие передачи помечаются внешними. Пользовательские storage вне штатных wrapper API и capability с переопределёнными методами требуют отдельных адаптеров.

Предмет в неизвестном/выгруженном/офлайн-хранилище не восстанавливается второй копией: нужно вернуть его в доступное учтённое место. Аварийное завершение процесса во время уже применяемого отката не покрыто постоянным журналом транзакции отката; резервные копии находятся в RAM. При штатной остановке незавершённый откат компенсируется до сохранения мира.

## Проверки

`./gradlew build` проверяет историю, обязательный cart-фильтр при копировании запросов, порядок ID при обратном ходе часов, 600 записей с пагинацией, груз, дроп и отклонение небезопасных планов, связанный обмен, курсор, баланс предметов и непрерывность слотов получателя через границы страниц, а также прежние очереди/журнал/доставку и обфускацию.

`./gradlew runServer -PcreateSmoke` запускает изолированный dev-only fixture с Create и AE2: native pack/save/load ID, восстановление блоков/предметов/жидкости, world commit, отмена и 32 связанных дропа; применение/компенсация получателя, выход до сохранения, отказ при конфликте, отказ при неизвестном/повреждённом компоненте предмета и прямое изменение стека штатным меню. Fixture не включается в выпускной JAR, не разрешает логирование без AuthCore и не проверяет полноценную запись в настоящий ClickHouse. Для проверки нагрузки, авторизованного журнала и остальных модов нужен отдельный прогон на сервере с AuthCore и Spark.

Дополнительно fixture выполняет штатный подбор дропа (`playerTouch`) и передаёт его снимки через настоящий построитель плана и координатор: полный/частичный подбор, заполненный инвентарь, задержка, компенсация при отмене, конфликт слота и повторное появление уже подобранной сущности. Проверки истории охватывают несколько получателей, разрыв цепочки, несходящийся баланс, отсутствие события создания и смешанную цепочку «подбор → меню конструкции».


Для автоматизации добавлены проверки протокола предметов/жидкостей, баланса компонентов, неполных/повторных частей, адресации сторон, разрывов цепочки и связанных событий через 601 запись истории. HTTP fixture проверяет сохранение обоих внешних снимков в COMPAT даже при отключённых подробностях обычных событий.

Native fixture выполняет 16 сценариев автоматизации: предметы и жидкости × выдача, приём, частичное принятие, отмена, конфликт содержимого, замена BlockEntity, выгруженное внешнее хранилище и блокировка. Используются реальные переносные интерфейсы Create, одиночный сундук и `SmartFluidTank`; адреса фиксируются и при попадании в заранее заполненный `BlockCapabilityCache`. Снимки проходят настоящий построитель плана и координатор. Проверяется отказ строгого codec жидкости и текст подробностей GUI. AuthCore в стенде отсутствует: штатный журнал не включается; fixture передаёт отделённые native снимки через тот же протокол. Это не полноценный прогон авторизованной записи в живую БД или отрисованного клиентского GUI.

`./gradlew runServer -PbackpackSmoke` проверяет совместный запуск с Create, Backpacked и Framework. `./gradlew cleanCompileCreateSmokeJava compileCreateSmokeJava runServer -PbackpackSmoke -PbackpackAbsent -PcreateAbsent` проверяет запуск без Create, Backpacked и Framework. Тестовый набор не включается в выпускной JAR; зависимости остаются необязательными.


## Этап 1 подготовки 2.2.0: двойные сундуки

Связанные автоматические передачи теперь адресуют ванильный двойной сундук одинаково при обращении к любой половине и стороне: позиция правой половины, общий слот 0–53, состояние и тип BlockEntity обеих половин. В GUI добавлены адрес второй половины и физический слот 0–26 с его позицией. Несколько обращений к тому же слоту внутри операции объединяются в одну пару снимков. Поддержаны только точные штатные классы сундука и порядок CompoundContainer; произвольные/перевёрнутые обёртки не принимаются. Если доступ к штатной структуре контейнера недоступен, адаптер отката отключается без предположений о порядке слотов.

Откат проверяет обе половины, размеры, компоненты и количество. При отсутствии чанка, замене/разделении сундука либо изменении любой половины в пересекающейся истории блоков откат отклоняется. Обе уже загруженные половины удерживаются и резервируются, включая новые capability-обёртки и созданные вручную CompoundContainer, содержащие зарезервированную половину. Соседние машины приостанавливаются для обеих половин. Запись, поиски, построение плана и декодирование продолжают использовать существующие фоновые пути; обходов мира/инвентаря на обычном тике не добавлено.

Тестовый fixture расширен до 41 сценария автоматизации; новые случаи охватывают обе половины, обычный сундук/ловушку, входящий/исходящий обмен, частичное принятие, отмену, компоненты, смену/разделение половин, блоковую историю второй половины, каноническую адресацию и новые/ручные обёртки. Отдельно проверены крайние номера слотов и непрерывность снимков двойного сундука. Проверки выполняются без выпускного JAR; состояние проверок фиксируется в `docs/RELEASE_2.2.0_PLAN.md`.
